# Trust Auditor Review — 2026-09-11

**Verdict:** mixed-signals

This is an honestly-framed personal project — the README and CONSTITUTION.md both set modest, non-commercial expectations, and the project delivers on that: active commit cadence, an attribution section that credits upstream sources by name, and a semver/tagging discipline enforced by CI. But two concrete, falsifiable promises the constitution itself makes are currently false — the CLAUDE.md line-count success criterion is violated, and the `panel-product` skill this very review is generated by is advertised in the README as a working quarterly review while the project's own tracked milestone documents it as never having produced a committed run and carrying known design defects. Neither is deceptive in intent (both are visible in the repo's own issue tracker), but a stranger reading only the README would not learn either fact.

## Findings

**[HIGH] Constitution's own mechanically-checkable success criterion is currently false**
- Stated claim: CONSTITUTION.md § Success Criteria: "The repo's CLAUDE.md stays under ~250 lines (context-scarcity discipline)."
- Observed reality: `/Users/chris/devel/home/claude-code-plugins/CLAUDE.md` is 297 lines (`wc -l` verified directly against the working tree), roughly 19% over the stated ceiling. The constitution itself is dated "Last refreshed: 2026-05-16," predating the plugin-split (`a8540c8 feat!: split the cacack plugin into five focused plugins`) and subsequent feature additions (graft, issue-standards) that plausibly pushed CLAUDE.md past the line.
- Trust cost: this is exactly the kind of claim a careful stranger would spot-check (it's binary, cheap to verify, and explicitly framed as "how we'll know this is working") — and it fails on the first check. It undercuts confidence in the rest of the success-criteria section, none of which is otherwise independently verified in the snapshot.
- Suggested action: either trim CLAUDE.md back under 250 lines, or update the stated ceiling to reflect the actual post-split size and note why it grew (a personal repo is free to revise its own bar — but it should say so rather than leave a stale, failing number on the books).

**[HIGH] README advertises `panel-product` as a working feature; project's own milestone says it has never run and has known design gaps**
- Stated claim: README describes `panel-product` (shipped, versioned as part of `panels` 1.0.1) as producing "per-persona reports plus synthesis, a foil report, and proposed-issue drafts" on a quarterly cadence — presented identically to every other shipped skill, with no disclaimer.
- Observed reality: the open milestone "panel-product rework" (issues #71–#79, 9 open / 0 closed) states plainly: "`panels:panel-product` shipped at v1.0.0 and has never produced a committed run," and that a review "found that the panel's persona set is anchored to a rubric that does not cover it, that the panel produces no output comparable between runs, and that its five personas overlap enough to need explicit 'do not evaluate X' fencing." Issue #71 exists specifically to produce this review as the tool's first real-world exercise. Separately, the snapshot's own metadata line notes the skill was run at a version (1.0.1) that wasn't actually cached in the session — the operator had to apply the 1.0.1 label-probe and draft-format behavior manually per PR #80 — meaning even this very review is being produced by a workaround, not the shipped, cached behavior.
- Trust cost: a stranger installing `panels@cacack` on the strength of the README would reasonably expect `panel-product` to behave like the other listed skills (validated, exercised, stable-enough for its version number). Nothing in the README or plugin.json flags it as unexercised or under active rework. The gap is visible only by cross-referencing the issue tracker.
- Suggested action: add a one-line disclaimer next to `panel-product` in the README (or a version-scoped note) indicating it is newly exercised / under active rework until milestone "panel-product rework" closes, consistent with how the milestone itself already documents the gap.

**[MEDIUM] No CHANGELOG.md despite a formal, CI-enforced version-bump discipline**
- Stated claim: CLAUDE.md's "Version Management" section describes a rigorous per-plugin semver policy — mandatory version bumps before shipping, git tags per plugin (`<name>/vX.Y.Z`), and CI that "requires a version bump for each plugin whose files changed." This is real process discipline, evidenced by the tag list (`authoring/v1.2.1`, `authoring/v1.2.0`, `authoring/v1.1.0` in quick succession).
- Observed reality: CHANGELOG.md is absent (confirmed: `ls CHANGELOG.md` → no such file). A user who installs `panels@cacack` and later updates to a new tagged version has no artifact that says what changed, only raw git log / diff between tags.
- Trust cost: the versioning ceremony (bump + tag + push) implies "this project tracks releases carefully," but without a changelog a consumer can't act on that care without reading commit history plugin-by-plugin. This is a transparency gap between the process rigor implied and the consumer-facing artifact delivered.
- Suggested action: even a minimal `CHANGELOG.md` per plugin (or one root file with per-plugin sections) generated from tagged commit ranges would close the gap; low effort relative to the existing tagging discipline.

**[LOW] SECURITY.md absent despite the project building security-review tooling and running hooks/skills that invoke real tools**
- Stated claim: none — CONSTITUTION.md's Audience section explicitly excludes "enterprise teams expecting supported tooling," and Non-Goals disclaims becoming "a commercial or supported product." No security-support promise is made anywhere in the README.
- Observed reality: SECURITY.md is absent. At the same time, the collection ships `delivery:security-review`, `panels:engineering-security` (which itself audits "SECURITY.md adequacy" on other repos), and `authoring:audit-hooks` — i.e., the project builds and recommends security hygiene it doesn't apply to itself.
- Trust cost: minor, given the honest personal-project framing — most strangers evaluating a personal marketplace would not expect a disclosure policy. The mild irony (a toolkit that grades other repos' SECURITY.md while lacking its own) is worth noting but doesn't rise above a hygiene nit given the stated non-goals.
- Suggested action: optional — a one-line SECURITY.md ("personal project; file an issue, no disclosure SLA") would close even the appearance of the gap cheaply, but is not required by the project's own stated commitments.

**[LOW] Metadata inconsistency in how this very review's tool version was exercised**
- Stated claim: the marketplace table lists `panels` at version 1.0.1, implying the shipped, installable behavior a consumer gets is 1.0.1's.
- Observed reality: the snapshot's own header states "session had 1.0.0 cached; the 1.0.1 label-probe and draft-format behavior were applied manually — see PR #80," meaning the actual mechanism that produced this report deviated from what a normal install would exercise.
- Trust cost: minor and self-disclosed (which is itself a good transparency signal — the snapshot doesn't hide the workaround). Flagging only because a reader comparing this report's rigor against a future "clean" 1.0.1 run should know this run wasn't one.
- Suggested action: none required beyond what's already disclosed; consider noting in the eventual `panel-product` output whether a run used a cached vs. patched skill version, for future run-over-run comparability (this overlaps with open issue #75, "Diff each panel-product run against its predecessor").
