# Audience Advocate Review — 2026-09-11

**Verdict:** partially-served

**Stated audience (from CONSTITUTION.md):** "This is for: Chris Clonch, the maintainer, as primary user; secondarily, other developers comfortable with Claude Code who treat this as a reference implementation for plugin patterns; and, through the `principles` plugin's universal profile, people doing non-code work with Claude who receive the canon without ever installing this marketplace." Explicitly excluded: "beginners new to Claude Code, enterprise teams expecting supported tooling, or anyone who needs Anthropic-blessed canonical patterns."

Three audiences with three different surfaces. The primary audience (the maintainer) mostly experiences this project through the `/play → /do → /ship` daily-driver cycle, and that cycle has one live, tracked defect that silently corrupts output — a real audience-surprise for the one person this project must not fail. The secondary audience (developers studying this as a reference implementation) lands on a README that is a thorough skill catalog but gives them no orientation to the *why* — the mission, the explicit exclusions that would let them self-select in or out, or the design docs that are the actual reference material — before they start reading source. The tertiary audience (non-code canon recipients) never touches this repo's surfaces directly, and the one skill that serves them (`principles:instill`) is carefully worded for that handoff, which is worth crediting rather than flagging.

## Findings

**[HIGH] The primary audience's daily-driver tool silently produces wrong commits**
- Constitution audience: "Chris Clonch, the maintainer, as primary user" — the person who runs `/play → /do → /ship` on every piece of work this repo does on itself.
- Observed evidence: Milestone "run-prompt concurrency safety" (snapshot lines 200-207): "`delivery:run-prompt` dispatches a parallel execution group as concurrent subagents into one git worktree, so they share a single index and their staging and commit operations race. A commit can land carrying one prompt's message with another prompt's file contents, and **nothing fails loudly when it does**." Tracked as issue #50, `priority:high`, `value:high`, open since 2026-07-19, unscheduled until this milestone was created.
- Audience cost: The maintainer expects a commit to contain what the prompt that authored it actually did. Instead, under the documented failure mode, a commit's message and diff can come from two different prompts with no error, no warning, and no visible signal — the exact "audience would expect X and find Y" pattern this review looks for, on the tool used for essentially every change in this repository.
- Suggested action: None needed from this review — #50 already exists with the right severity and a closure condition. Flagging here only to confirm the audience-experience lens agrees with the roadmap's own prioritization.

**[MEDIUM] README gives the secondary audience no way to self-select before installing**
- Constitution audience: secondary audience is "other developers comfortable with Claude Code who treat this as a reference implementation," explicitly excluding "beginners new to Claude Code, enterprise teams expecting supported tooling, or anyone who needs Anthropic-blessed canonical patterns."
- Observed evidence: Per the snapshot's README excerpt, the README opens with "My personal Claude Code plugin collection" but "notably absent from the README: the mission statement, the audience definition (including the 'this is not for' exclusions), the non-goals, and any pointer to `CONSTITUTION.md`." A confirmed read of `README.md` shows Installation, Plugins (a full skill/agent catalog), Scripts, Attribution, and References sections — no section states scope, no link to `CONSTITUTION.md` anywhere in the file.
- Audience cost: A developer arriving via GitHub search or a link has one line ("My personal ... collection") to infer scope from. They cannot learn, without leaving the README, that this project explicitly isn't trying to be enterprise-supported or Anthropic-canonical — the two exclusions most likely to cause a mismatched expectation later (e.g., filing a support-style issue, or assuming these are "the" recommended patterns rather than one maintainer's opinionated set). The intended secondary audience benefits from this framing too: knowing the project is explicitly "iterate over perfecting" and non-canonical changes how much weight to give any one pattern as "the reference."
- Suggested action: One sentence plus a link — e.g., a line under the title pointing to `CONSTITUTION.md` for scope/audience/non-goals — costs a few lines and closes the gap without turning the README into a second constitution.

**[MEDIUM] The design docs a reference-implementation reader most wants are buried inside one plugin's skill list**
- Constitution audience: secondary audience explicitly "treat this as a reference implementation for plugin patterns" — their value moment is understanding *why* the patterns look the way they do, not just that a skill named `create-hooks` exists.
- Observed evidence: Snapshot: "The design docs (`handyman-principle.md`, `design-guidelines.md`) are linked only in passing from within the `authoring` section." Confirmed in `README.md` line 110: "This plugin also owns the design docs behind the collection: the [Handyman Principle](plugins/authoring/docs/handyman-principle.md) and [design guidelines](plugins/authoring/docs/design-guidelines.md)." — the only appearance of either link in the whole file, positioned as a footnote to the `authoring` plugin's skill list rather than as top-level orientation for the collection's design philosophy (which CLAUDE.md itself treats as foundational: "Resources follow the Handyman Principle... Key guidelines").
- Audience cost: A developer studying this repo for plugin-pattern ideas has to read through Installation, the full `delivery` skill list, and the full `panels` skill list before reaching the one paragraph that tells them *why* the patterns are shaped the way they are. Someone skimming (which is exactly how a "reference implementation" browser behaves) is likely to miss it entirely.
- Suggested action: Surface the two design-doc links near the top of the README (e.g., alongside or just after the opening line), not only inside the `authoring` section.

**[MEDIUM] No sample output for the reference-implementation audience to evaluate a pattern before running it**
- Constitution audience: secondary audience studies "plugin patterns" — for a multi-persona panel or a generated `CONSTITUTION.md`, the pattern's value is largely in its *output shape*, not its invocation syntax.
- Observed evidence: Snapshot: "No usage examples beyond install commands; no sample output." Confirmed: `README.md`'s only runnable content is the marketplace-add/install block (lines 7-19); every skill entry is a one-line description of what it does, never what it produces. (This review's own artifact — `docs/reviews/panel-product/2026-09-11/` — is a committed example of `panel-product` output, but it is not linked from the README or referenced as a sample.)
- Audience cost: To judge whether, say, the `panel-review` 6-subagent pattern or the `constitution` skill's fixed five-section output is worth adapting into their own project, a developer currently has to install the plugin and run it against their own repo — real friction for a "just want to see the pattern" evaluation, and disproportionate compared to the low cost of linking one existing, already-committed example.
- Suggested action: Link one or two already-committed example outputs (e.g., a past `docs/reviews/panel-product/` or `docs/reviews/panel-engineering/` run, a sample `CONSTITUTION.md`) from the relevant README skill entries.

**[LOW] No CHANGELOG.md for a reference-implementation audience tracking pattern evolution**
- Constitution audience: secondary audience "treat this as a reference implementation for plugin patterns" across a project that is actively iterating (Principle 4: "iterate over perfecting").
- Observed evidence: Snapshot "Other top-level docs": "CHANGELOG.md: **absent**." Five independently-versioned plugins exist (`authoring` v1.2.1, `delivery` v1.0.0, `panels` v1.0.1, `principles` v1.0.0, `toolbox` v1.0.0), each with its own tag history (e.g., `authoring/v1.1.0`, `authoring/v1.2.0`, `authoring/v1.2.1`).
- Audience cost: A developer who adopted a pattern from an earlier version and wants to know what changed (e.g., "what changed between `authoring/v1.1.0` and `v1.2.1`?") has no changelog to read and must reconstruct it from `git log`/tag diffing — a workable but non-obvious path for someone who "installs only what they need" rather than clones the whole history.
- Suggested action: Optional given project scale; a minimal per-plugin changelog (even just release-note bodies on the git tags) would close this cheaply if it becomes a recurring ask.

## Notes

- The tertiary audience — "people doing non-code work with Claude who receive the canon without ever installing this marketplace" — is handled with real care at the one seam that matters: `plugins/principles/skills/instill/SKILL.md` explicitly tells the installer to "Never assume. At user scope, **ask**" when choosing between the `engineering` and `universal` profiles, "that is exactly the case where a non-developer is being set up," and the `universal.md` payload itself (`plugins/principles/principles/profiles/universal.md`) is written in code-free, generalized language appropriate to that audience. Since this audience never touches the repo's own docs, there is little more to evaluate here — noted as a positive rather than a finding.
- `CONTRIBUTING.md` describes a pre-plugin-split repository layout (root-level `agents/`, `commands/`, `skills/` — the structure before `a8540c8` split the project into five plugins) and is stale against the current `plugins/<name>/...` structure. This is left out of scope here as contributor-onboarding territory (`engineering-dx`'s beat, not the stated audience's), but is flagged for cross-reference in case it falls in the gap between personas.
- Issue templates (`.github/ISSUE_TEMPLATE/{bug,spike,story,task}.yml`) and a `config.yml` disabling blank issues give the secondary audience a reasonable way to file a well-formed issue if they hit a problem — a genuine help surface, not a gap.
